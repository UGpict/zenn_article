[AI Hackathon（AIHACK）](https://aihackathon.jp/)で「ふたりログ」というデート計画アプリを作りました。二人の希望を聞いて一日の行程を組み、雨や遅延で予定が崩れたら組み直し、デートの振り返りを次回に活かすWebアプリです。計画するのは一人で、相手はアプリを使いません。

公開デモ（Cloud Run）: https://futari-log-w5a2hgpkiq-an.a.run.app

この記事では、なぜこの課題を選んだか、AIエージェントをどう設計したか、そしてビジネスとしてどこへ伸ばせるかを書きます。技術的にいちばん頭を使ったのはエージェントの設計なので、そこを厚めに解説します。

## なぜ「デート計画」なのか

「行き先が決まらない」はデートの一番の悩みです。ここは体感ではなく調査に裏づけがあります。

Z世代を対象にした調査（PROMOTION+B、2025年2月公開）では、デートの悩みの上位が次のようになっていました。

| デートの悩み | 割合 |
| --- | --- |
| デート場所が決まらない | 36.7% |
| 行き先ややることが分からない | 26.5% |
| お金がかかる | 30.9% |

悩みの中心が「どこへ行くか」に集まっています。「お金」も上位ですが、これは15〜19歳の男性でとくに高く出ています。同じ調査で「事前に行き先を決めておく」人は全体で36.2%、25〜29歳の男性に絞ると55.6%。この年代の男性は準備にこだわる層で、まさにターゲットです。

もう一つ、男女で認識がずれている点も見逃せません。少し古い調査（KDDI、2010年、20〜30代800名）なので数字はそのまま鵜呑みにできませんが、傾向として示唆的です。デートプランを決めるのは自分だと答えた男性が51%いる一方、男性が決めてくれていると感じている女性は27%にとどまりました。女性の80%が「男性が優柔不断でマンネリ化している」と答え、デート案内サービスを使いたい人は75%以上でした。

要するに、**男性側は「決めなきゃ」と気負っているのに、相手にはうまく伝わっていない**。この非対称を埋めるのが狙いです。

AIで解くことへの追い風もあります。20代男性の生成AI利用率は71.0%で全世代最高（ロイヤリティマーケティング、2026年5月調査）。AIにデートプランを任せることへの抵抗が、この層ではすでに小さい。加えて「デートプランは二人で一緒に決めたい」という働く男性が3割近くいる調査（マイナビウーマン、2016年）もあり、「ふたりで作る」というコンセプトの後押しになります。

## ふたりログがやること

課題を踏まえて、アプリの役割を三つに絞りました。

- **決める**: 二人の希望・予算・日時・固定予定から、実在するスポット3〜4件の行程を生成する
- **直す**: 雨・満席・移動遅延といった変化に対して行程を組み直す
- **憶える**: デートの振り返りを分析し、承認された内容だけを次回のプランに反映する

このうち技術的に難しいのは「決める」と「直す」でした。AIを噛ませれば作れそうに見えて、実際に安定して動かすには工夫がいります。

## AIエージェントの設計：肝は「肝心なときにAIを呼ばない」

AIアプリなのに、いちばん大事な瞬間にはAIを呼びません。これがふたりログの設計の芯です。**ユーザーを待たせる場所にLLMを置くと、遅くて不安定になる**という、作ってみて分かった単純な事実がきっかけでした。

料理店にたとえると腑に落ちるかもしれません。注文が入ってから食材を市場に買いに走る店は、どれだけ腕が良くても提供が遅い。いい店は営業前に仕込みを済ませておき、注文が来たら手早く盛り付けます。ふたりログも同じで、時間のかかる情報集めは裏で仕込んでおき、ユーザーの前では組み立てるだけにしました。

### 壁：初回プランに66秒かかった

最初に動くものを作った段階では、プラン生成の中でGeminiに検索（grounding）を同期で呼んでいました。これが致命的に遅かった。Cloud Run上で初回プランの所要を実測すると、次のとおりです。

| 区間 | 所要 |
| --- | --- |
| run 作成 → 完了 | 66,148 ms |
| クライアントPOST → 画面反映 | 68,129 ms |

66秒のうち約51.7秒が同期のGemini groundingでした。デートの予定を一つ立てるのに1分以上ローディングを眺めるのは、デモでも実利用でも成立しません。

犯人はLLMのレイテンシでした。呼ぶたびに応答が数秒から数十秒まで振れ、検索を挟むとさらに伸びます。しかも「どの店を、どの順番で、何分ずつ回るか」という行程づくりは、ひらめきよりパズルに近い。営業時間に収まるか、移動を足しても予算と時間に収まるか、二人の「これは外せない」条件に反しないか。条件を照らし合わせれば答えは決まります。

### 解決：「仕込み」は裏で、「盛り付け」は一瞬で

そこで処理を、仕込みと盛り付けの二つに分けました。

**盛り付け＝ユーザーが待つ経路（LLMなし）**。希望・記憶・営業時間・移動時間を照らし合わせて行程を組む決定論プランナーだけを置きます。ここではAIを一切呼ばず、実行ログ上もモデルは `deterministic/planner`、トークン消費はゼロです。速いうえに、同じ入力なら毎回同じ結果が返ります。

**仕込み＝材料を集める経路（LLMあり）**。イベント収集、料金の裏取り、振り返りの分析といった時間のかかる仕事は、バックグラウンドのエージェントに任せます。Cloud SchedulerやWorkflowsから非同期で動かし、集めた材料はFirestoreに貯めておく。次にプランを組むときは、その仕込み済みの材料を決定論プランナーが読むだけです。

このとき、LLMの呼び出しは[OrcaRouter](https://www.orcarouter.ai/ja)を共通の入口にまとめ、用途に応じてモデル（GeminiやGPT系）を振り分けています。今回は基本的な使い方にとどまりましたが、複数のモデルを一箇所で切り替えられる作りは、こうした仕込みと分析の使い分けと相性がよさそうです。

![ふたりログの全体像。上段「プランを作る」はAIを使わずルールで行程を組み、下段「裏側で情報をためる（自動）」がGeminiで会場・料金を仕込む。右側は出かけたあとの振り返り→記憶→次回反映のループ](/images/futari-log/architecture.png)
*上段がユーザーの待つ経路（AIなし）、下段が裏で回る仕込み（Gemini）。行程づくりの本線からLLMが外れているのが見てとれる。*

この分離で、ユーザーの待ち時間とLLMのレイテンシが切り離されました。同期groundingを外した前後で、初回プランの所要は **66,148 ms → 17,854 ms**（約73%短縮）。LLMを「使わない」のではなく「ユーザーが待たない場所で使う」に置き換えただけで、体験の重さがほぼ消えました。

### 行程は「賢さ」ではなく「計算」で決める

決定論といっても候補を並べているだけではありません。組んだ行程を検証し、違反があれば候補を差し替えて再検証するループが入っています。

東京の各エリアで実際に走らせたとき、渋谷では最初の行程が検証に引っかかりました。営業確認の取れた候補に1回だけ差し替え、再検証を通してから確定しています。ログ上は `VALIDATION_FAILED` → `SELF_CORRECTED`（1回）→ `PLAN_APPLIED` という流れです。

営業時間の判定にも工夫があります。祝日はGoogle Placesの通常営業時間だけ見ると休業扱いになりがちですが、当日日付が一致する `currentOpeningHours` を優先することで祝日営業を正しくOPENと判定できます。敬老の日に走らせたとき、通常営業では月曜休館だった美術館が、当日日付つきの営業情報で開館として行程に載りました。

### ブレーキ①：分からないことを、埋めない

AIに任せると危ういのが、知らないことをそれっぽく埋めてしまう癖です。そこでふたりログには二つのブレーキをかけました。

一つ目が、事実を根拠（Evidence）に紐づけて管理する仕組みです。料金や営業時間が取れないときは、0や空文字で埋めずにUNKNOWNのまま残します。LLMが提示しただけの未知のスポットIDは、そのまま行程に採用しません。

つまり「予算内かどうか不明」なら「予算内」とは言わない。デモ映えのために都合よく事実をでっち上げない、という一線を型（zod）とバリデーションで縛っています。ハッカソンだと数字を盛りたくなりますが、ここを正直に作ったことがそのまま信頼性になりました。

### ブレーキ②：AIの学びは、承認してから効かせる

二つ目のブレーキが、記憶の承認です。振り返りの分析はLLMの担当ですが、その出力を直接プランに流し込みません。振り返りエージェントが「次は座れる休憩を多めに」といった記憶の候補を作り、**ユーザーが明示的に承認したものだけ**が型付きのディレクティブ（例: `PREFER_SEATED_REST`）として次のプランに効きます。

![振り返りエージェントが記憶候補を作り、ユーザーの承認を経て次回プランに反映されるループ](/images/futari-log/memory-loop.png)
*振り返り → 記憶候補 → 承認／却下 → 次回プランへ反映、というループ。承認しなければ何も残らない。*

実測でも、この記憶のありなしで滞在の組み方が変わることを確認しました。同じ材料でプランを組み直すと、立ちっぱなしになりやすいスポットの滞在が50分から35分に丸められ、その差分はすべてこのディレクティブで説明がつきました。LLMの気まぐれを、承認済みの構造化データという一段のクッションでユーザー体験から遠ざけています。

## ビジネスとしての伸びしろ

作って終わりではなく、事業としての筋も考えています。

**マネタイズはサブスクリプションと、イベント会社からの広告の二本柱**を想定しています。ポイントは広告の出し方です。バナーを貼るのではなく、デートプランそのものに提携先の会場やイベントを組み込む。ユーザーは「良いプラン」として受け取り、そのまま送客につながるので、広告が顧客化に直結します。

さらに先の展望として、**相手（女性側）の意見を汲み上げる仕組み**があります。振り返りから相手の好みが構造化されて溜まっていけば、デートプランの精度が上がるだけでなく、記念日のプレゼント提案のような別の価値にもつなげられます。「二人の記憶」を持っていることが、そのまま次のサービスの資産になります。

## もらったフィードバックと、これからの方向性

実際に触ってもらって、いくつも示唆的な声をもらいました。方向性を決めるうえで大きかったので、そのまま残しておきます。

**使う人数を広げられそう**、という声がありました。今は「二人の関係」を前提にしていますが、複数人で使える形にすれば、たとえば女性の友達同士で遊びの計画を立てる、といった使い方にも広がります。二人用に閉じず、行き先を決めあぐねる場面全般に効くツールとして育てる余地があります。

いちばん考えさせられたのが、**「見られ方」への配慮**です。彼女とのデートがどうだったかを彼氏が入力し、それが彼女にも見えると思うと、次のデートで気まずくならないか、嫌な思いをさせないかと、書く側が身構えてしまう。異性からの見られ方を気にする人は実際に多い、という率直な指摘でした。

この点について、ふたりログは今のところ**振り返りをPRIVATEに保ち、相手と共有しない設計**にしています。相手はアプリを使わず、外部に出すのは日時・集合場所・公開してよい行程だけをまとめた共有用の下書きに限っていて、採用理由や振り返り、内部ログは渡しません。「誰が何を見られるか」はプロダクトの信頼に直結するので、機能を足すときもこの線は慎重に引きたいところです。

そしてターゲット像も見えてきました。機嫌を取り合ったり見栄えを気にしたりする関係よりも、**「この人とこれから一緒に過ごしていきたい、二人でいい関係を作り上げたい」と思っている人**にこそ刺さる、という声です。ここを軸に磨いていきたいと考えています。

## 余談：ここに辿り着くまでの3.5日

きれいに書いてきましたが、実際の開発はかなり泥臭かったので、正直に残しておきます。

そもそもデート計画は最初のテーマではありませんでした。初日は「葬式をエージェントで解決しよう」と息巻いてスタートしています。ところが二人ともその領域のドメイン知識がなく、悩みに悩んでも刺さる形が一向に見えてこない。片方が熱を出すほど詰めても空振りが続き、ようやく恋愛・デートというテーマに舵を切って手応えが出ました。3.5日の開発期間のうち、まる1日はほぼ前に進んでいません。

チーム構成もなかなかの綱渡りでした。二人ともフロントエンドしか触ったことがなく、かろうじて少しだけバックエンドをかじっていた自分が、API周りをまるごと引き受けることに。そこからは1日17時間くらい手を動かし続けて、締め切りにギリギリ滑り込みました。

学びを一つ挙げるなら、**自分たちが解像度を持てる課題を選ぶこと**です。知らない領域はAIエージェントの前に、まず自分が何を作ればいいのか分からない。テーマ選びで1日溶かしたぶん、そこは次に必ず活かします。

## まとめ

ハッカソンでAIを組み込むとき、つい「どう賢く使うか」に意識が向きます。今回いちばん効いたのは逆で、「どこで使わないか」を決めたことでした。

- 行き先が決まらないという課題は、調査でも裏づけのある確かな痛みだった
- 行程を確定する部分は決定論に寄せると、速くて結果が安定する
- LLMは材料集めと分析に回し、非同期で貯めておく
- 事実は根拠に紐づけ、不明はUNKNOWNのまま。記憶は承認を経てから効かせる

ユーザーが待つ経路とLLMのレイテンシを切り離し、事実を正直に扱う。この二つを徹底したことで、締め切りの中でも「速くて信用できるAI」に仕上がりました。

## 謝辞

このプロダクトは[AI Hackathon（AIHACK）](https://aihackathon.jp/)で開発しました。場を用意してくださった運営のみなさん、そしてLLMの共通入口として使わせていただいた[OrcaRouter](https://www.orcarouter.ai/ja)に感謝します。

一つ、正直に驚いたことを書いておきます。開発中はデバッグのためにLLMをひたすら叩き続け、消費トークンは数億規模に達しました。それだけ回してもOrcaRouter側の費用は9ドルほど。このコスト効率は素直にすごいと思いました。OrcaRouter自体は今回まだ簡易的な使い方にとどまっているので、次はモデルの振り分けやコスト最適化まで踏み込んで活かしたいと考えています。
